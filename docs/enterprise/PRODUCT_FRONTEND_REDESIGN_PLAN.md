# 企业知识管理与可信查询平台：产品与前端重构方案

> 状态：实施基线
> 更新时间：2026-08-17
> 适用实现：Java DDD 企业版 + 现有 Preact Web

## 1. 目标

当前 Java 版已经具备较完整的知识底座：资料上传、版本、证据、统一检索、摘要、实体归一、关系图谱、企业百科、知识质量评估、用户与权限、审计、MCP 等能力。当前主要问题不是底层能力缺失，而是产品层仍然按技术模块拼装：问答和高级检索重复、筛选逻辑重复、普通用户暴露过多技术名词、资料/任务/证据之间缺少连续操作流、后端已有高级知识生成能力但前端缺少完整运营闭环。

本轮重构不重新设计底层架构，不替换现有 Java DDD，不删除 Wiki/Graph，不削弱 Evidence-first 约束。目标是把已有能力整理成一款可长期使用的企业知识产品。

产品定位统一为：

**企业知识管理与可信查询平台**

围绕两条主线：

1. 企业资料持续进入系统，经过解析、索引和高级知识生成，成为可追溯知识资产。
2. 企业员工通过一个统一入口查询知识，得到带原文依据的回答，并可继续浏览百科、关系和原始资料。

核心生命周期：

```text
资料进入
  -> 资料信息确认
  -> 解析与索引
  -> 可查询
  -> 高价值判断
  -> 高级知识生成
     -> 摘要
     -> 事实校验
     -> 完整性检查
     -> 实体归一
     -> 关系生成
     -> 企业百科
  -> 知识查询 / 企业百科 / 关系图谱
  -> 原文证据
  -> 用户反馈 / 质量评估
  -> 持续改进
```

## 2. 参考产品后的设计原则

本方案吸收企业知识产品和开源知识库中已经验证的边界，而不是直接复制某一产品的页面。

### 2.1 员工使用面

参考企业搜索/知识产品的共同做法：员工不需要判断自己应该“问答”还是“搜索”。对员工只有一个知识查询入口，系统在一次查询中完成检索、证据确认和回答生成。

因此：

- 删除“企业问答”和“高级检索”作为两个并列用户入口的设计。
- 统一为“知识查询”。
- 高级检索能力迁移为管理员的“检索测试”。
- 普通查询页面不暴露 BM25、RRF、Rerank、Raw 等检索内部实现。

### 2.2 知识管理面

参考成熟知识库管理产品：资料首先是可管理的业务资产，而不是数据库记录。

因此：

- “资料”成为知识资产的主工作对象。
- 上传、元数据、版本、解析内容、知识生成和证据都围绕资料组织。
- 普通用户允许上传时，上传入口直接位于“资料管理”，不再创建独立上传中心。
- 管理员和普通用户共享资料管理能力，但管理权限不同。

### 2.3 知识生成面

参考结构化知识生成产品：摘要、实体、关系、百科不是独立孤岛，而是同一条高级知识生成链。

产品统一使用“知识生成”概念，不再在普通界面使用 Distillation、Promotion、Source、Claim、Grounding、Coverage 等非必要英文。

## 3. 产品语言规范

### 3.1 基本原则

除行业已经高度通用、翻译反而降低理解效率的技术名词外，产品界面使用中文。

可以保留：

- PDF / Word / PPT / Excel
- API / MCP / HTTP
- MySQL / MinIO / OpenSearch / Neo4j
- Embedding / Rerank（仅管理员技术配置和检索测试页面）

产品层统一中文：

| 技术或旧名称 | 产品名称 |
| --- | --- |
| Document | 资料 |
| Version | 版本 |
| Evidence | 证据 |
| Raw Block | 原始知识片段 |
| Summary | 摘要 |
| Claim | 知识陈述 |
| Wiki | 企业百科 |
| Graph | 关系图谱 |
| Grounding | 事实校验 |
| Coverage | 完整性检查 |
| Source | 来源资料 |
| Distillation | 知识生成 |
| Promotion / Recommendation | 生成推荐 |
| Entity Resolution | 实体归一 |
| Relation | 关系 |
| Pipeline | 处理流程 |
| Retrieval Test | 检索测试 |
| Retrieval Trace | 检索过程 |
| Evidence-backed | 有证据支撑 |
| Evidence-first | 证据优先 |
| Effective Hit | 有效引用 |

代码内部类型和接口不要求为了 UI 中文化而强制改名，避免无意义迁移；但所有用户可见文本遵循上述规则。

## 4. 角色模型

V1 继续保持两个角色，不扩展复杂 RBAC：

### 4.1 普通用户

默认能力：

- 知识查询
- 企业百科
- 关系图谱
- 资料浏览
- 查看自己的上传记录
- 查看查询引用原文

当管理员打开“允许普通用户上传资料”后增加：

- 上传文件、文件夹、ZIP
- 在开始入库前调整自己批次中的逐文件资料信息
- 查看自己的上传进度
- 重试自己的失败文件

### 4.2 管理员

拥有普通用户全部能力，并增加：

- 始终允许上传
- 查看全部资料、入库记录和知识生成
- 知识运营首页
- 高级知识生成
- 知识质量
- 检索测试
- 用户与权限
- 审计日志
- 系统设置

管理员关闭普通用户上传开关时，不影响普通用户已经入库资料的查询和浏览。

## 5. 信息架构

### 5.1 普通用户导航

左侧导航保持扁平，不再为了概念完整度增加分组标题。普通用户依次看到：

```text
知识查询
企业百科
关系图谱
资料管理
上传记录
```

普通用户登录后默认进入“知识查询”。

不向普通用户提供独立“证据中心”一级入口。引用来源通过知识查询、企业百科和关系图谱自然进入。

### 5.2 管理员导航

管理员同样使用扁平导航，“首页”固定放在最上方：

```text
首页
知识查询
企业百科
关系图谱
资料管理
入库记录
知识生成
检索测试
审计日志
用户与系统
```

管理员登录后默认进入“首页”。首页承担知识资产、待办、质量和任务概览，不再额外套“知识运营”分组或名称。

导航设计原则：

- 一级入口数量可控时优先扁平化，不为只有一两个页面的分类制造分组。
- 首页属于全局入口，固定置顶，不作为某个业务分类下的子项。
- 菜单只展示图标和名称，不再附带解释性副文案。
- 独立技术页只有在管理员确实需要操作时才进入一级导航。

## 6. 知识查询

### 6.1 定位

“企业问答”和“高级检索”合并为唯一员工查询入口“知识查询”。

一次用户查询只对应一个业务问题和一个查询记录。目标链路：

```text
问题 + 知识范围
  -> 统一检索
  -> 证据确认
  -> 回答生成
  -> 回答 + 引用资料 + 相关知识
```

长期目标是回答和诊断视图共享同一个 `search_id`，禁止为了展示检索结果重新执行一遍独立查询。

### 6.2 页面结构

```text
知识查询

[ 请输入想了解的企业问题........................ ] [查询]
知识范围：全部资料  [调整范围]

回答
--------------------------------------------------
自然语言回答 [1][2]

资料依据
--------------------------------------------------
[1] 原文摘录 / 资料定位 / 查看原文
[2] 原文摘录 / 资料定位 / 查看原文

相关知识（有则展示）
--------------------------------------------------
相关企业百科
局部关系图
```

第一版直接复用当前 Ask API 的回答和引用能力，不增加第二次检索。

### 6.3 知识范围

全站只定义一套知识范围数据模型和一个前端组件。

V1 已支持字段：

- 公司
- 来源部门
- 文档类型
- 材料分类

后续补充：

- 文档日期范围
- 标签

知识查询中采用折叠式简洁展示；检索测试中采用完整展开式展示。底层字段和状态管理必须复用同一组件。

## 7. 检索测试

### 7.1 定位

原“高级检索”迁移为管理员“检索测试”，不再是普通用户功能。

用途：

- 验证某个问题能否召回正确资料
- 分析召回来源
- 比较检索策略调整前后的结果
- 定位“没有召回 / 召回错误 / 排序错误 / 证据解析失败”等问题

### 7.2 可展示专业信息

该页面属于管理员/知识运营人员，因此可以保留必要技术信息：

- 原文 / 摘要 / 企业百科 / 关系图谱的候选类型
- BM25
- Embedding
- RRF
- Rerank
- 排序前后位置
- 最终证据解析结果

但“为什么命中”必须来自真实后端检索过程，不能继续使用前端字符串包含判断伪装成召回解释。

第一版先删除或弱化当前前端伪“为什么命中”表达；后续由后端返回真实检索过程结构。

## 8. 资料管理

### 8.1 定位

资料是核心知识资产。普通用户和管理员都进入同一个“资料管理”，权限决定可见操作。

### 8.2 列表页

主要能力：

- 搜索资料
- 按公司、来源部门、文档类型、材料分类筛选
- 按版本状态筛选
- 添加资料（有上传权限时）
- 进入资料详情

管理员后续增加：

- 按知识生成状态筛选
- 按上传人筛选
- 按是否建议生成高级知识筛选
- 按失败状态筛选

### 8.3 资料详情

从当前右侧小面板升级为真正的资产详情页/大抽屉，至少包含：

```text
资料信息 | 内容 | 版本 | 知识生成 | 证据
```

资料信息：

- 资料名称
- 原文件名
- 公司
- 来源部门
- 文档类型
- 材料分类
- 文档日期
- 标签
- 上传人
- 上传时间

内容：

- 展示解析后的章节/段落结构
- 支持直接定位原文

版本：

- 版本号
- 当前状态
- 创建时间
- 版本切换关系

知识生成：

- 原文解析
- 检索索引
- 摘要
- 事实校验
- 完整性检查
- 实体归一
- 关系生成
- 企业百科

证据：

- 当前版本证据数量
- 证据列表
- 原文定位

## 9. 普通用户上传资料

### 9.1 权限

继续沿用现有全局开关：

- 关闭：只有管理员可上传
- 开启：所有 ACTIVE 普通用户可上传

不新增复杂上传角色。

### 9.2 两阶段流程

保持现有正确设计：

1. 上传 / ZIP 安全解压 / 进入暂存区
2. 用户确认逐文件资料信息后再真正开始解析和入库

### 9.3 第一步：选择资料

支持：

- 多文件
- 文件夹选择
- ZIP
- 拖拽普通文件

只有在浏览器真正实现目录递归后才宣传“拖拽文件夹”；当前若只支持目录选择，则文案必须准确。

### 9.4 第二步：确认资料信息

批次默认字段：

- 公司
- 来源部门
- 文档类型
- 材料分类
- 文档日期
- 标签

下一阶段增加自动建议：

- 从目录路径推断
- 从文件名推断
- 从文档首页/结构推断
- 根据企业知识模板推断

自动建议必须明确标明来源，用户可以覆盖。

### 9.5 大批量编辑

当前 1500px 超宽表格不适合 500-2000 文件。目标改成虚拟表格，并提供：

- 全选 / 当前筛选全选
- 批量设置公司
- 批量设置部门
- 批量设置文档类型
- 批量设置材料分类
- 批量设置日期
- 批量添加标签
- 只看异常
- 只看重复
- 只看缺少信息
- 只看自动识别结果

### 9.6 重复/版本提示中文化

内部状态保留，产品显示：

- CREATE_DOCUMENT -> 新资料
- CREATE_VERSION -> 新版本
- REUSE_VERSION -> 内容完全一致，将复用已有版本
- DUPLICATE_CONTENT -> 检测到相同内容，可继续独立入库或归并到已有资料

## 10. 资料管理、上传记录、入库记录与知识生成

四个入口必须按照“资产”和“过程”严格分边界。

### 10.1 资料管理：管理资产

资料管理回答“系统现在有哪些资料、当前哪个版本可用、这些资料已经生成了哪些知识”。上传中的资料可以显示处理中，但资料管理不再展示批次列表和入库任务详情。

### 10.2 上传记录：普通用户查看自己的入库过程

普通用户只看自己发起的上传批次和文件处理状态，核心用途是确认“我刚上传的资料处理完了吗”。

前端简化为：

```text
待确认 -> 等待处理 -> 处理中 -> 已完成 / 失败
```

文件详情可以显示保存文件、解析资料、整理内容、建立检索等易懂阶段。失败时展示可理解原因和“重新处理”。待确认批次可以在这里直接“继续配置”。

### 10.3 入库记录：管理员查看全局入库过程

管理员查看所有用户的上传批次，额外显示上传人，并负责处理积压、失败和待确认批次。

入库范围到资料完成解析、建立原始检索并成为可用资料为止。摘要、关系、百科不属于入库完成条件。

### 10.4 知识生成：管理员查看高级知识生成过程

知识生成只展示已经入库资料之后的高级知识生成记录，例如：

- 摘要生成
- 事实校验
- 完整性检查
- 实体归一
- 关系生成
- 百科生成

资料上传、MinerU 解析、Embedding、索引和版本激活不进入“知识生成”。后端任务查询必须按 `source=COMPILE` 过滤，不能在前端分页后再过滤。

## 11. 高级知识生成

产品统一称“知识生成”，不再使用“构建任务”这类既像动作又像名词的表达。

不再显示“高价值 Source / Distillation / Promotion”。

生成推荐展示为：

> 该资料近期被频繁有效引用，建议生成摘要、关系和百科知识。

状态：

- 未生成
- 建议生成
- 生成中
- 已完成
- 部分失败
- 需要更新

真实目标流程：

```text
ACTIVE 资料版本
  -> 生成推荐
  -> 后台生成任务
      -> 摘要生成
      -> 事实校验
      -> 完整性检查
      -> 实体归一
      -> 关系生成
      -> 百科生成
      -> 百科关系投影
      -> 质量评估
```

当前 Java 编译 API 为同步 HTTP，后续必须改为 durable task。编译时间可能达到分钟级，不应长期占用前端请求。

第一版前端不得把 Summary 完成伪装成 Graph/Wiki 完成。当前 `wikiReady={summaryReady}` / `graphReady={summaryReady}` 必须移除或改为“状态暂不可用”，直到后端返回真实阶段状态。

## 12. 企业百科

### 12.1 定位

企业百科是员工可主动浏览的知识资产，不是调试器。

默认使用阅读模式：

- 正常章节文章
- 知识陈述在正文中自然呈现
- 引用使用 [1] [2] 形式
- 点击引用打开证据和原文

管理员可进入“可信链”查看：

- 知识陈述
- 事实校验
- 时间状态
- 事实 ID
- 证据 ID

第一版保留当前功能，优先完成中文化和入口整理；阅读/可信链双模式作为下一阶段。

## 13. 关系图谱

### 13.1 定位

关系图谱服务两个场景：

1. 用户主动探索企业、人员、合同、机构之间关系。
2. 知识查询结果中辅助理解局部关系。

### 13.2 目标交互

- 平移 / 缩放
- 拖动节点
- 节点类型区分
- 关系类型筛选
- 1 层 / 2 层扩展
- 时间过滤
- 点击节点继续展开
- 点击关系查看关系详情和证据
- 高亮当前查询路径

当前固定 SVG 网格布局作为 V1 临时实现，后续升级为真正交互式局部图谱。

## 14. 证据与原文

证据不是普通用户一级导航，而是所有知识的可信底座。

进入路径：

- 知识查询引用 -> 证据 -> 原文
- 企业百科引用 -> 证据 -> 原文
- 关系图谱关系 -> 证据 -> 原文
- 资料详情 -> 证据 -> 原文

当前 PDF 页码 + bbox 定位保留。

后续增强：

- Word：章节 / 段落定位
- PPT：页定位
- Excel：工作表 / 区域定位
- Markdown/Text：段落高亮
- HTML：结构化文本块定位

## 15. 知识运营首页

管理员首页不再以技术架构宣传为主，回答“现在有什么需要处理”。

优先展示：

- 资料处理失败
- 建议生成高级知识
- 百科需要更新
- 知识质量异常
- 用户负反馈

其次展示知识规模：

- 资料数
- 版本数
- 原始知识片段数
- 企业百科数
- 关系数

再展示真实质量指标：

- 事实校验通过率
- 完整性检查通过率
- 实体归一准确率（有评测时）
- 百科证据覆盖率

禁止制造没有真实样本依据的“综合 AI 评分”。

## 16. 知识质量

新增管理员一级运营能力，聚合已有和后续质量机制。

### 16.1 生成质量

- 摘要事实校验
- 摘要完整性
- 实体归一
- 关系校验
- 百科证据覆盖

### 16.2 检索质量

- Golden 测试
- 检索回归
- 无结果查询
- 失败查询

### 16.3 用户反馈

知识查询结果增加：

```text
这次查询是否解决了你的问题？
[有帮助] [有问题]
```

问题分类：

- 没找到需要的资料
- 找到的资料不相关
- 资料正确但回答有误
- 回答不完整
- 引用原文有问题
- 企业资料本身存在冲突

反馈必须关联：

- 用户问题
- search_id
- 最终答案
- 检索结果
- 证据 ID
- 反馈类型

### 16.4 Golden Evaluation

把现有 Java artifact evaluation 接入页面，展示摘要、关系、实体、百科和证据覆盖的真实指标，并支持不同构建策略之间的回归比较。

## 20. 本轮验收标准

Phase 1 完成后必须满足：

1. 普通用户看不到“企业问答”和“高级检索”两个冲突入口，只看到“知识查询”。
2. 普通用户仍可进入资料管理，并在管理员打开上传开关后直接添加资料。
3. 普通用户默认页是知识查询；管理员默认页是知识运营首页。
4. 检索测试只对管理员显示和开放。
5. Ask 和检索测试复用同一知识范围组件和同一字段顺序。
6. 一级导航不再提供“证据中心”，但所有现有证据查看和原文定位能力不受影响。
7. 用户界面不再大面积混用 Evidence / Grounding / Coverage / Distillation / Source 等非必要英文。
8. 资料详情不再用 Summary 状态伪造 Wiki / Graph 已完成。
9. 前端 TypeScript + production build 通过。
10. Java 后端和现有数据链路不被破坏。

## 21. 明确不做的事情

本轮不做：

- 不删除 Go baseline。
- 不更换 MySQL / MinIO / OpenSearch / Neo4j。
- 不升级 MinerU。
- 不引入多租户和复杂部门 ACL。
- 不新增几十种角色。
- 不为了页面好看伪造知识质量分数。
- 不把同步编译 API 包一层假进度条冒充后台任务。
- 不为了中文 UI 强制重命名所有 Java 内部类和数据库字段。

本方案后续作为产品与前端演进的优先基线；实现过程中发现底层接口无法支撑真实产品状态时，应补真实接口，而不是在前端猜测状态。
