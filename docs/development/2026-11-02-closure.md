## 旧 FAILED5 如何处理

当前**没有**让同输入第五次失败任务因新 JAR / 新 wire DTO / 新模型 profile 而直接重新生成的解禁入口；不把改名、repair、命令或切换 profile 当新预算。旧合同原任务和越额别名不可重置 attempt 或凑第六次。后续如需“修复协议后的人工重验”机制，应单独确定策略和审计规则，本批没有擅自加入。

原正常新输入路径仍在：真正修改来源形成新版本，或真正的来源 ACL 修订；Raw 重解析只有实际 parser pipeline 身份变化才会保留新解析版本，同原件 SHA + 同 pipeline 的重复重解析复用旧结果。这些入口不能仅为逃避失败次数而制造变化。本批真实新 Summary 使用之前从未生成过的独立验收说明，旧合同的实际越额行为另行隔离，二者明确区分。

模型收据和事实记录绑定了协议、原任务、epoch 及输入；**数据库收据没有 JAR SHA 的内建签名列**。本次生产者 JAR 由独立不可变部署回执、进程出生时间、任务开始时间、冻结源码与实际 Hash 交叉绑定；最后读回的 reader JAR 与原 producer JAR 分别记录。不能称为数据库内密码学产物证明，也不能倒填最后 JAR 为历史生产者。
